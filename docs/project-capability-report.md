# 乐奇 AI 助盲眼镜：功能与阶段成果汇报

## 1. 项目概述

乐奇 AI 助盲眼镜面向盲人和低视力用户，目标是让用户通过眼镜实体键和语音完成导航、环境观察、入口查找、菜单阅读及按需的可见表情辅助，而不必在行走过程中查看手机屏幕。

系统采用“眼镜 + 手机 + 领域核心 + 可替换 AI 服务”的协作方式：

```text
盲人用户
  │ 实体键 / 语音 / 第一视角图像
  ▼
Rokid 眼镜薄客户端
  │ DeviceTransport
  ▼
Android 手机伴侣
  │ 统一事件、Tool 和事实合同
  ├── 地图与定位 Provider
  ├── ASR / TTS Provider
  └── ObservationGateway
        ├── OCR
        └── VLM（视觉语言模型）
  ▼
SessionOrchestrator + 安全策略 + 语音仲裁
```

当前阶段已经完成供应商无关的应用骨架、合同、会话编排、安全执行边界、模拟器和自动化测试。高德 Web 导航演示可以运行；真实眼镜、手机定位、麦克风、播报及在线模型仍需后续接入和真机验证。

## 2. 用一个盲人餐厅场景说明系统功能

下面以“用户独自前往约定餐厅”为例，说明应用如何把各端接口和模型能力串起来。

### 第一步：说出目的地

用户按下眼镜实体键，系统播报“请说目的地”。用户说：“去约定的餐厅。”

1. 眼镜或手机麦克风采集语音；
2. ASR 将音频转换为文本；
3. `SpeechInputProvider` 将结果归一化为 `SpeechInput`，包含会话 ID、文本、置信度、语言、来源和意图；
4. `SessionOrchestrator` 在 `destination_input` 状态产生 `search_destination` 效果；
5. `ToolGateway` 校验 Tool 白名单、版本、会话状态、参数 Schema 和幂等键；
6. `NavigationProvider.search()` 搜索附近 POI；
7. 系统通过语音读出候选餐厅，请用户确认。

已完成：统一语音输入接口、Fake ASR、高德 POI 搜索适配器、Fake 导航、Tool 安全校验和目的地状态推进。

待接入：真实麦克风、真实 ASR、手机实时定位和语音候选选择。

### 第二步：开始步行导航

用户说“确认”后，手机计算步行路线并开始播报关键节点。

1. `navigation.confirm_destination` 只提交稳定的候选 ID，不传递高德 SDK 对象；
2. `navigation.start` 启动导航；
3. 地图适配器产生 `NavigationEvent`，例如接近转弯、偏航、定位弱、接近路口和到达；
4. `NavigationReminderPolicy` 将导航事实转换为简短中文 `SpeechEffect`；
5. `SpeechPriorityPolicy` 按“风险 > 导航 > 普通说明 > 细节”排序播报。

例如，普通导航详情正在播报时，如果出现偏航或定位异常，风险提示会优先处理。地图层只提供路线事实，不直接控制眼镜，也不自行决定安全等级。

已完成：高德 Web 步行路线、导航 Provider、关键提醒策略、语音优先级队列和过期语音清理。

待接入：高德 Android 导航 SDK或其他实时导航 SDK、真实 GPS、后台持续定位和真实 TTS。

### 第三步：接近路口并检查信号灯

手机检测到前方路口，系统播报：“前方约二十米即将到达路口，需要检查时请按键或说检查。”

系统此时不会自动拍照。只有用户按键或说“检查”后才继续：

1. `SessionOrchestrator` 从 `navigating` 进入 `intersection_check`；
2. 用户确认后，系统产生 `request_observation(vision.traffic_signal)`；
3. `ToolGateway` 检查该操作是否处于允许状态，并验证明确授权；
4. `DeviceTransport` 向眼镜发送 `capture.requested`；
5. 眼镜拍照并返回 `capture.completed + media_id`；
6. `ObservationGateway` 按 `capability_id` 将图像交给 VLM；
7. 模型结果被归一化为 `ObservationResult.facts[]`，例如：
   - `traffic_signal.state`；
   - `traffic_signal.direction_match`；
   - `crosswalk.present`；
   - `vehicle.activity`；
8. 领域策略根据事实、置信度和有效期生成等待、重查、谨慎辅助或无法判断的提示。

即使视觉结果为绿灯，系统也不能承诺“安全通行”；它只能提供保守辅助，并要求用户继续注意周围车辆和声音。红灯、方向不匹配、车辆接近、低置信度、事实过期或未知结果都不能被模型改写为可通行结论。

已完成：路口能力注册、用户确认门槛、设备事件合同、观察事实结构、风险语音优先级和场景状态推进。

待接入：真实眼镜拍照、图像传输、路口 VLM、事实质量评测和真实道路封闭测试。

### 第四步：到达餐厅并寻找入口

地图报告已到达目的地附近后，系统只提醒：“请按键观察入口”，不会自动拍摄。

用户按键后，系统调用 `vision.entrance`。VLM 可以返回招牌、门的位置、台阶或画面遮挡等可见事实。若画面模糊或置信度低，系统要求用户调整方向后重拍；只有结果满足条件时，会话才从 `entrance_check` 进入 `inside_restaurant`。

已完成：入口能力、低置信度重拍分支、入口状态推进、统一 VLM 适配器。

待接入：入口提示词与结构化输出定义、真实模型、不同光照和门型数据集测试。

### 第五步：读取菜单并继续追问

进入餐厅后，用户按键拍摄菜单。系统调用 `vision.menu`：

1. OCR 识别菜单文字；
2. `OcrObservationAdapter` 将供应商结果归一化为 `menu.text_line` 事实；
3. 系统先播报菜单摘要；
4. 用户可以继续问“有没有不辣的？”；
5. 对话模块只能依据当前会话中已确认的菜单事实回答，不能编造菜品。

已完成：OCR 适配接口、菜单事实归一化、菜单会话状态和观察结果播报。

待接入：真实 OCR、菜单版面分析、菜品属性抽取、多轮事实查询和餐厅实拍评测。

### 第六步：按需提供可见表情辅助

用户明确说“帮我看看对面的人表情”后，系统才调用 `vision.expression`。

模型只能描述单帧中可见的粗粒度表现，例如“嘴角上扬，可能在微笑”，并必须说明不确定性。系统不进行身份识别，不推断真实情绪、性格或心理状态，也不能在用户未请求时主动拍摄他人。

已完成：表情能力注册、明确请求门槛、会话状态和 VLM 统一接口。

待接入：真实模型、隐私提示、媒体自动删除和合规评测。

## 3. 应用层接口如何协作

| 应用阶段 | 核心接口或合同 | 输入 | 输出 | 当前实现 |
|---|---|---|---|---|
| 语音输入 | `SpeechInputProvider` | 麦克风音频或模拟文本 | `SpeechInput` | 接口 + Fake ASR |
| 搜索目的地 | `NavigationProvider.search` | `DestinationQuery + 当前位置` | `DestinationCandidates` | 高德 Web + Fake |
| 计算路线 | `NavigationProvider.walkingRoute` | 起点和终点坐标 | `WalkingRoute` | 高德 Web + Fake |
| 导航提醒 | `NavigationReminderPolicy` | `NavigationEvent` | `SpeechEffect` | 已实现并测试 |
| 播报仲裁 | `SpeechPriorityPolicy` | 多个 `SpeechEffect` | 有序播报队列 | 已实现并测试 |
| 手机—眼镜通信 | `DeviceTransport` | `DeviceCommand / MediaTransfer` | `DeviceEvent` | 接口 + Simulator |
| 设备事件归一化 | `DeviceEventMapper` | 眼镜原始按键、拍摄、播报事件 | 标准 `DeviceEvent` | 已实现并测试 |
| 视觉观察 | `ObservationProvider` | `ObservationRequest` | `ObservationResult.facts[]` | 接口 + 网关路由 |
| OCR | `OcrObservationAdapter` | 图片引用 | 文字事实和 OCR 项 | 适配骨架 + Fake 测试 |
| 场景视觉 | `VlmObservationAdapter` | 能力 ID、图片引用和上下文 | 摘要、事实、风险 | 适配骨架 + Fake 测试 |
| 会话编排 | `SessionOrchestrator.handle` | 语音、导航、设备、观察事件 | 结构化领域效果 | 已实现并完成黄金场景回放 |
| Tool 执行 | `ToolGateway.execute` | `ToolCall + SessionState` | `ToolResult / ContractError` | 已实现并测试 |
| 合同校验 | JSON Schema + AJV | 跨端消息与 Tool 参数 | 通过或结构化错误 | 构建期 + 运行时 |

应用层的基本约束是：`SessionOrchestrator` 不直接导入 Android、高德、Rokid、OCR 或 VLM SDK；它只读取标准事件并产生结构化效果。所有具体供应商都位于 Provider 或 Gateway 之后，因此替换模型或地图供应商不需要重写核心会话。

## 4. 模型功能汇报

### 4.1 ASR 与意图归一化

ASR 负责把用户语音转换为文字和置信度。上层可以进一步识别目的地、确认、查询、重复、取消和表情辅助请求。低置信度语音应触发澄清，不能直接执行高风险动作。

### 4.2 VLM 场景理解

当前注册了五个视觉能力：

| 能力 ID | 模型任务 | 输出重点 |
|---|---|---|
| `vision.scene` | 通用场景观察 | 障碍物、方向性描述和局限 |
| `vision.entrance` | 入口查找 | 招牌、门、台阶、相对方向 |
| `vision.menu` | 菜单理解 | 文字、菜品、价格和可查询属性 |
| `vision.expression` | 可见表情辅助 | 粗粒度可见表现和不确定性 |
| `vision.traffic_signal` | 路口视觉事实 | 信号灯、方向匹配、斑马线、车辆活动和有效期 |

VLM 不能直接修改会话状态、发送设备命令或给出安全保证。它只返回事实候选，最终提示由确定性策略生成。

### 4.3 OCR 菜单识别

OCR 负责提取菜单中的文字行。后续可以增加版面分析、菜名/价格配对、辣度和过敏原提示，但回答必须来源于已识别事实；画面不清晰时应请求重拍。

### 4.4 LLM/Agent 决策

LLM 可以协助理解自然语言、选择已注册能力、生成摘要或提出 ToolCall。它只能看到白名单 Tool，实际调用还必须经过 `ToolGateway`：

```text
LLM 提出 ToolCall
  → 检查 Tool 与版本
  → 检查调用来源和当前状态
  → 检查用户授权
  → AJV 校验参数
  → 检查截止时间和幂等键
  → 限时执行 Handler
  → 返回 ToolResult 或 ContractError
  → 写入审计记录
```

模型不能直接调用摄像头、地图、CXR、蓝牙、任意网络请求或 TTS，也不能伪造观察结果和导航状态。

## 6. 所需硬件与设备信息

### 6.1 Rokid 眼镜

需要确认或提供以下信息：

- 眼镜准确型号、硬件版本、系统版本和固件版本；
- 使用 JSUI、Ink 或其他运行时，以及对应 SDK 版本；
- 是否允许第三方应用访问相机、麦克风、扬声器和实体键；
- 实体键 ID，以及短按、长按、双击的原始事件格式；
- 摄像头支持的分辨率、图片格式、自动对焦和单帧拍照延迟；
- 音频播放能力、音量控制、打断和完成回调；
- 电量、温度、前台/后台运行及资源占用限制；
- 是否支持 ADB、开发者模式、日志导出和应用安装调试。

### 6.2 手机与 Android 环境

至少需要一台用于联调的 Android 手机，并确认：

- 手机型号、Android 版本和厂商系统版本；
- 蓝牙、Wi-Fi、USB 或厂商通道中实际采用哪一种连接方式；
- 后台定位、麦克风、蓝牙和通知权限策略；
- 高德 Android SDK 所需的包名、签名 SHA-1 和 Key；
- 是否允许前台服务长期保持导航和眼镜连接；
- 锁屏、息屏、省电模式和网络切换时的行为。

### 6.3 手机—眼镜传输资料

若使用 Rokid CXR 或系统通道，需要：

- 官方 SDK、Demo、API 文档和授权说明；
- 配对、连接、断线重连和多设备管理流程；
- 消息格式、请求 ID、确认机制和错误码；
- 单条消息大小、MTU、图片分片和二进制传输方式；
- 延迟、吞吐量和媒体传输超时建议；
- 相机、音频与官方应用之间的资源抢占规则。

在资料不完整时，可以继续使用 `SimulatorTransport` 完成业务开发，但不能宣称真机链路已经可用。

### 6.4 现场测试辅助设备

建议准备：

- 耳机或眼镜扬声器，用于评估户外语音可懂度；
- 移动电源和温度记录方式，用于长时间续航测试；
- 网络热点或双 SIM 手机，用于测试弱网和断网降级；
- 室内入口、菜单、玻璃门、台阶等可控测试场景；
- 封闭或有工作人员保护的模拟路口。路口功能在完成安全评测前不得直接用于开放道路通行决策。

## 7. 所需模型与服务信息

真实服务接入前，需要确定以下选型。密钥只能写入本地 `.env` 或密钥管理服务，不能提交到 Git：

| 服务 | 需要的信息 |
|---|---|
| ASR | 厂商、模型名、流式/短语音接口、语言、鉴权、超时、费用和隐私策略 |
| VLM | 厂商、模型名、图片格式与大小限制、结构化 JSON 能力、延迟、费用和数据保留政策 |
| OCR | 厂商、菜单/中文支持、版面能力、置信度字段、限流和费用 |
| TTS | 厂商或系统 TTS、中文音色、打断能力、离线能力和播放完成回调 |
| 地图 | 高德 Web/Android SDK Key、应用包名、SHA-1、服务配额和步行导航能力 |
| Agent/LLM | 模型名、Tool Calling 格式、上下文限制、结构化输出、内容安全和数据策略 |

## 8. 当前边界和后续里程碑

### 已经可以证明

- 领域接口和多端合同能够编译并自动校验；
- 导航、提醒、设备、观察和会话可以通过 Fake/Simulator 串成完整黄金场景；
- Tool 调用已经具备权限、授权、状态、Schema、幂等和超时边界；
- 高德 Web API 可以替换 Fake 导航完成 POI 搜索和步行路线查询；
- CI 能阻止类型、测试和合同错误进入主分支。

### 尚不能宣称

- 眼镜真机已经稳定拍摄、播报和传输图片；
- 手机能够在后台持续稳定定位和导航；
- 真实 ASR、OCR 或 VLM 已达到盲人场景可用精度；
- 系统可以可靠避障或判断过街安全；
- 表情能力能够判断人物真实情绪；
- 整套系统已经完成真实用户、隐私、安全和无障碍验收。

### 推荐下一步

1. 确定 Rokid 型号、SDK 和手机—眼镜通信方案，先完成按键、拍照、播报的真机闭环；
2. 接入手机真实定位和地图导航事件；
3. 确定 ASR/TTS 服务，跑通完全无屏的目的地输入与确认；
4. 优先接入入口或菜单能力，完成第一条真实视觉闭环；
5. 建立图片脱敏、自动过期、日志脱敏和用户授权机制；
6. 在可控环境中进行弱网、断连、低光、模糊、噪声和低置信度测试；
7. 路口辅助最后接入，并先限定在封闭测试场景内评估。

## 9. 汇报结论

项目目前已经从“文档和接口设想”推进为一套可运行、可回放、可自动验证的应用层骨架。盲人用户从说出目的地，到导航、路口确认、寻找入口、阅读菜单和按需请求可见表情辅助的流程，已经能够用标准事件、Tool、Provider 和模拟器完整串联。

下一阶段的重点不是继续扩展更多模型概念，而是把现有接口逐个替换为真实硬件和真实服务，在严格的用户授权、安全策略和可控测试环境下验证延迟、准确率、稳定性与无障碍体验。
