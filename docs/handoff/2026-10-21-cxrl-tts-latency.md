# v0.4.2 语音等待优化与对比测试

## 已确认的真机结果

2026-10-21 用户补充确认：测试方已经完成三轮语音，也已完成物体拍摄，图片描述及眼镜请求代号均对应。此信息作为现场补充确认记录，不修改原始 JSON，也不再把缺少第三轮导出当成已证实的软件故障。

本次处理的是语音合成等待慢。v0.4.1 的两条完整语音日志中，从录音结束到软件开始播放分别为 10.946 秒和 8.453 秒，其中 TTS 合成为 9.764 秒和 7.143 秒。此前报告的约 1.2 / 1.3 秒只算到开始合成，不能代表开始出声。

## 本版改动

- v0.4.1 等整段回答合成完才播放；v0.4.2 优先合成短首段，准备好便开始播放，播放期间预先合成下一段。
- 首段目标不超过 16 个 Unicode 码点，后续目标不超过 40 个，优先在自然标点处切分；连续英文单词和数字可能使段落超过目标长度。拼接所有段落等于完整原文，不缩短、漏读或改写回答，也不提高播放倍速。
- 最多保留一段正在播放的音频，以及一段已准备或合成中的后续音频，不排队积累整段 PCM。
- 取消、切后台、失败和超时停止播放、清除预加载音频，晚到的合成结果不进入新一轮。麦克风仍采用明确开始、半双工模式。
- 新增 `first_audio_ready`、`tts_chunks`、`tts_strategy` 和 `tts_compute_ms`，便于从 JSON 比较首段等待及实际合成耗时。
- Gemma、SenseVoice、MeloTTS 权重和采样率保持原版；当前仍采用 CPU 两线程 TTS，避免在未取得手机线程对比结果前盲目加线程。

改善重点是首次出声等待。分段可能改变停顿和语气；如果手机合成仍慢于播放，段间也可能等待，因此需要同时评价“多久开始”和“是否连贯”，不能只看首段速度。桌面基准不能替代小米 15 Pro 的实测。

## 下载和覆盖安装

[发布页：cxrl-speech-v0.4.2](https://github.com/wwq031/AI-glass-for-blind/releases/tag/cxrl-speech-v0.4.2)

从发布页下载两个 `.apk.part`、`manifest-v0.4.2.json` 和 `restore-cxrl-apk.ps1` 到一个新文件夹，在该文件夹执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\restore-cxrl-apk.ps1
```

将合并出的 `phone-l-speech-v0.4.2.apk` 复制到手机覆盖安装。所有权重仍在 APK 中，无需另行下载；新版复用已校验的同一权重缓存，但启动仍需校验和加载。手机建议保留至少 12 GB 空间。

## 本次只需重点比较这些项目

1. 在同一小米 15 Pro、手机扬声器路由和近似温度条件下测试。先确保两类模型就绪，停止其他录音或播放。
2. 点击“测试离线语音播报”，固定话术为“你好，离线中文语音播报测试。现在是二零二六年。”，记录首次等待和听感。首次单独记录，再连续测试两次；每次等全部播完。
3. 做一轮正常语音问答和一次图片结果朗读。检查后半段没有丢失、重复、串入旧回答，也没有长时间段间停顿。实际听到后点击听见确认。
4. 在首段播放时取消，再开始一句新的问答；检查没有继续播放旧内容。再做一次进入后台、返回后重新操作。
5. 完成后导出 JSON；附一段能够听见手机实际输出的外部录像。无需为这次 TTS 对比重新做整套三轮上下文和三张图片验收。

## 日志口径

- `first_audio_ready - tts_start`：首段合成就绪等待。
- `play_start - record_end`：对话结束录音到软件请求首段播放，包含 ASR、Gemma 及首段合成等待；不等于外部实测首次发声。
- `tts_compute_ms`：各段合成调用实际耗时之和，不含等前段播放完才继续预加载的时间。
- `tts_end - tts_start`：全部段落合成完的墙钟时间；新版本可能与播放重叠，不能再当成纯计算耗时。
- `play_end`：所有段落播放结束；只有整轮成功后才允许人工听见确认。

真实模型桌面基准：安装固定 `sherpa-onnx==1.13.8` 和 numpy 后执行 `python tools/benchmark-cxrl-tts.py`，使用公开固定文本比较整段合成、短首段合成和 2 / 4 线程配置。该脚本不录音、不访问用户照片或对话，也不在 CI 中模拟手机速度。
