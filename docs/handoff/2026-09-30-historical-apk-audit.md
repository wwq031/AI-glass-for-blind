## 三、三个致命问题

### 问题 1：APK 与项目设计完全不对接（最严重）

仓库里存在完整的 agent 核心：`packages/domain/agent/`（`session-orchestrator` / `llm-agent` / `plan-validator` / `tool-gateway` / `task-runner`），配套 `packages/contracts/` 合同层，P0 离线验收 124/124 通过。

**APK 从未引用过它，也从未实现它的合同。** 证据：

| APK 的蓝牙事件 | 在 `contracts` 中 |
|---|---|
| `voice.arm` | 0 命中 |
| `audio.start` | 0 命中 |
| `play.done` | 0 命中 |

Agent 侧的词汇是 `agent-plan` / `effect` / `observation.request` / `navigation.intersection_approaching` / `crossing-advisory` —— APK 里一个都没有。

APK 实际上自造了一套平行实现：自己的事件名 + `NavigationTask.State` Java 状态机 + 直连高德 SDK。

**而 agent README 恰恰写明："Android 手机服务、地图 SDK、语音服务，以及本地或云端模型 Provider 尚未完成端到端接入"** —— 也就是说，APK 本该做的是**适配器层**，它却把业务逻辑又实现了一遍。

这条信息量最大，也最应该在第一小时就告诉用户。它决定了后面所有工作的价值判断。

### 问题 2：核心播报链路里的崩溃 bug

```kotlin
OfflineTts(context.assets, config)   // 错误：模型走文件系统绝对路径，却传了非 null assetManager
```

后果（实测日志）：

```
W sherpa-onnx: You are using an absolute path '...model.int8.onnx', but assetManager is NOT set to null.
F sherpa-onnx: Read binary file: Load '...model.int8.onnx' failed
→ ApplicationExitInfo: reason=1 (EXIT_SELF) status=255
```

**原生层直接 `exit()`，整个 App 进程死亡。** Java 层的 `try/catch` 无法捕获——也就是说，"点一下检查按钮"这个动作会把 App 点崩。

这段代码被计为"已完成"。它显然**从未被真实执行过一次**。

### 问题 3：诊断按钮会撒谎（模型路径缓存）

`OfflineTtsBridge.modelDir` 在构造时解析一次，实例被 Activity 长期缓存（仅 `onDestroy` 释放）。因此**补上模型文件后，不重启进程，检查按钮会一直报旧结论**。

审计过程中，接手方已把文件放对位置，按钮仍然报"缺少文件"——直到强杀进程重启才正确。这解释了为什么前一轮"修了还是不行"的循环难以收敛：**工具本身在误导人**。

## 四、交接文档中的具体错误

文档整体是谨慎的，但关键处有错，且直接导致接手方多走弯路：

1. **"首要阻塞：模型文件由 shell 创建，App 无法访问"——判断过宽。**
   实测：Gemma 所在的 `files/models/` 是 App 自建目录（owner `u0_a276`），**App 可读**，Gemma 检查按钮当时就是**成功**的。真正读不到的只有 `models/tts/` 这一个子目录（shell 建，owner `shell`）。
   文档把一个局部问题写成了全局结论。

2. **建议的 Gemma 转移路径按文档执行会失败。**
   文档说"把 Gemma 复制进应用内部目录即可"。实测：`resolveModelFile()` 按 **外部优先** 顺序返回第一个能 `stat` 成功的候选。外部文件 Java 层能 `stat` 成功（所以会一直被选中），但**原生 `open()` 被拒**（`PERMISSION_DENIED`）。
   因此**只往内部复制是不够的**——必须同时把外部那份移走，解析器才会回落到内部。照文档做，"修完"依然失败。

3. **`/data/local/tmp` 中转缺了权限步骤。**
   文档给的 `adb push` → `run-as cp` 路径可行（push 出来的文件是 `-rw-rw-rw-`）。但用 `adb shell cp` 生成的中转文件继承源权限 `-rw-rw----`（owner `shell`），**App 读不了**，`run-as cp` 报 `Permission denied`。文档没有提这一点。

4. **真正的原因（原生 `open()` 与 Java `stat()` 行为不一致）没有被识别。** 这是作用域存储/FUSE 的典型陷阱，也是"文件明明在那儿却读不到"的根本解释。

## 五、该前一轮任务确实做对的部分

为保持公允，以下是**实测有效、有真机证据**的产出，并非全无价值：

- 双端 RFCOMM 自有蓝牙通道（不依赖 Wi‑Fi、不需 CXR 企业授权）——真机往返已验证
- 眼镜端录音（3 秒 / 96044 字节 WAV）、音频播放（AudioTrack）、拍照
- 手机端音频帧收发与播报队列（串行、去重、有界，设计是合理的）
- `TaskTag` 跨设备任务编号，解决"取消后迟到录音被误当本轮"的竞态——这是有质量的工程设计
- 离线 TTS 经接手方修正后**实测打通**：合成 44100Hz → 眼镜实播 261116 字节 → 回执 `play.done`
- 一批平台坑的记录：作用域存储与原生打开不一致、模型须落内部目录、高德 key 绑定 debug SHA1

**即：设备层是真的，业务层是重造的。**
